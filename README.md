# AI Infra Lab

A running log of learnings, work, and discoveries from building and operating self-hosted AI infrastructure — inference servers, benchmarking, evals, and the agent/application layer on top of them.

## Current Project: Self-Hosted LLM Inference Server

Self-hosted, OpenAI-API-compatible LLM inference stack on bare-metal GPU hardware, built from the ground up: hypervisor → GPU passthrough → driver/CUDA → Python/PyTorch → vLLM → served model.

**Stack:** RTX 5090 · Proxmox VE · Ubuntu 24.04 · CUDA 13.2 · PyTorch 2.13 · vLLM 0.29 · Qwen3.5-4B-FP8

**Status:** End-to-end path is working — GPU passthrough, driver/CUDA, PyTorch, vLLM, and the OpenAI-compatible API have all been validated. The VM now has a static IP (`192.168.60.157`, survives reboot) instead of DHCP. Phase A (single-request baseline) and Phase B (concurrency scaling) are both done — see [`benchmarks/`](benchmarks/). Concurrency ceiling is **highly prompt-size-dependent**: peak throughput/knee moves from ~15,400 tok/s @ concurrency 256 for trivial prompts down to ~180 tok/s @ concurrency 8 at ~9K prompt tokens — prompt size, not request count, is the real capacity constraint. **FP8 quantization tested and looks like a strict upgrade** over BF16 (official `Qwen/Qwen3-4B-Instruct-2507-FP8` checkpoint, needs a documented env-var workaround for an RTX-5090-specific vLLM bug) at both 32K and 128K context: faster decode, better-or-equal TTFT, more KV cache headroom, higher concurrency ceiling — speed/capacity only, quality wasn't evaluated. **Currently running: FP8 model at 128K context (`--max-model-len 131072`)** — same live config on `192.168.60.157:8000` as before this comparison started; restored automatically once the benchmark run finished.

**Model comparison round 1 done:** benchmarked three same-size-class candidates (`Qwen/Qwen3.5-4B`, `microsoft/Phi-4-mini-instruct`, `google/gemma-4-E4B-it`) against the incumbent, each in BF16 and FP8, at 32K and 128K context — see [`benchmarks/README.md`](benchmarks/README.md)'s "Model Comparison" section for the writeup and [`docs/MODEL_COMPARISON_RESULTS.md`](docs/MODEL_COMPARISON_RESULTS.md) for every raw number. **Qwen3.5-4B-FP8 looks like a genuine upgrade over the incumbent** — at a ~91K-token prompt (128K context), it's ~2.6x faster TTFT, ~2.1x faster decode, and has ~3.9x more KV-cache headroom/concurrency ceiling, most likely from hybrid linear-attention layers that don't pay the same long-context tax as standard attention. Phi-4-mini-instruct is competitive at 32K but its decode throughput collapses to ~11 tok/s at 128K (worse than the incumbent). Gemma-4-E4B-it has the best raw numbers of all four models on short prompts but **fails on 100% of requests longer than ~30 tokens** (immediate end-of-sequence, no server-side error) — reproduced and written up, likely a vLLM day-0-support gap for this brand-new architecture's attention backend, not a model defect.

**Model comparison round 2 done:** cast a wider net across vLLM's full supported-architectures list, verified against both the HuggingFace API and the live vLLM `ModelRegistry` — see `benchmarks/README.md`'s "Round 2" section and [`docs/MODEL_COMPARISON_ROUND2_RESULTS.md`](docs/MODEL_COMPARISON_ROUND2_RESULTS.md). No new champion. `ibm-granite/granite-4.0-h-micro`-AWQ (3.2B params) hits 350-437 tok/s decode at 128K/91K-token prompts — more than double Qwen3.5-4B-FP8 — but a same-day follow-up investigation found this doesn't hold up: it's **unreliable on any prompt under ~12,000 tokens, at any `--max-model-len`** (not a 32K-vs-128K config issue as first thought — direct testing proved the exact same short prompt fails identically at 128K too). The unquantized BF16 checkpoint shows the same failure signature at a much narrower range (~30-token prompts, content-dependent). Since a real conversation starts short, this rules the model out for production despite the excellent numbers at scale — see the corrected writeup for the full investigation (prefix-caching and CUDA-graph-replay both ruled out by direct A/B test). `LiquidAI/LFM2.5-2.6B` set a new project-wide throughput record (20,997 tok/s peak) but fails 100% of requests at 128K, same failure signature, not yet re-investigated the same way. Three other candidates (Falcon-H1-7B, Nemotron-H-8B-FP8, Ministral-3-8B) failed to load at all — a hard VRAM ceiling, a checkpoint/weight-loader incompatibility, and a `transformers`/vLLM version-skew bug, respectively, all written up as landmines. Also tested `--kv-cache-dtype fp8` (a KV-cache-only quantization, separate from every weight quantization tested so far) on the round-1 champion: **+90% KV-cache headroom, +15% decode throughput, for one flag, no new model** — the clearest "optimize at the software level" win found yet. As always: speed/capacity only, quality not evaluated — Phase E still gates any actual production switch.

**Same-day follow-up done:** went back to root-cause (not just document) two of round 2's landmines. **Ministral-3-8B's import bug is fixed** — a two-symbol `transformers`/vLLM version-skew bug in vLLM's vision-tower import path, patched with a small venv-scoped compatibility shim (a standing change to the production venv, documented in `docs/MODEL_COMPARISON_ROUND2_RESULTS.md`); the model now loads and serves cleanly at both 32K and 128K, though it trails Qwen3.5-4B-FP8 at every shape tested. Along the way, found its "FP8" and "BF16" checkpoints are byte-identical — Mistral's own release already ships natively mixed-precision, so there's no separate BF16 baseline for this model. **Nemotron-H-8B's official FP8 checkpoint is root-caused but not fixed**: vLLM 0.29 doesn't auto-detect this checkpoint's quantization config for this architecture at all, and refuses an explicit override — a real gap with no supported workaround this session. Separately, tried applying the proven `--kv-cache-dtype fp8` lever to both models (since neither has a working weight-FP8 path): **blocked on both**, by a different, genuine sm120 (RTX 5090) gap in FlashInfer's fused decode kernel — three mitigations tried, none worked. **Then tested the same flag against the actual live production model** (the original incumbent, not Qwen3.5-4B-FP8) — **it fails there too**, identical signature. 3 of 4 architectures tested this session hit this wall; only Qwen3.5-4B-FP8 works, and it's confirmed to be a genuinely hybrid linear+full-attention architecture, though that alone doesn't fully explain the difference (Nemotron-H is also hybrid and still fails). **This means `--kv-cache-dtype fp8` can't be adopted on production independently of a model switch — it's coupled to Phase E evals clearing Qwen3.5-4B-FP8 for production first**, not a parallel, lower-effort option as originally listed. Also did a fresh, rigorous "final check" against generic "best model for RTX 5090" advice (27B-70B quantized candidates) — all ruled out with real numbers (see `docs/AI_Inference_Server_Build_Log_and_Roadmap.md`'s Phase E section); none beat Qwen3.5-4B-FP8 for this box's actual requirements. Cleaned up ~55GB of confirmed-dead-end model downloads while at it.

**Phase E done (first pass):** the first *quality* eval in this project — every prior benchmark measured speed/capacity only. Built against the **real production tool registry** (`Operator-Portal`'s `LlmTools::Registry` — snow-zone reading reports, zone lookup, history queries, rate lookups), not an invented schema. Result: **Qwen3.5-4B-FP8 clears its first quality gate.** 39/42 vs. the incumbent's 33/42 overall (after tightening the grader — see the doc's "Grader correction" section for a real methodology lesson from that process), and the real story is the safety-relevant subset — 9/12 vs. **3/12**. The incumbent **fabricated a snowfall depth reading** (`inches: 2.5`) when the user gave no amount, on the one tool that writes to payroll-linked records, and on a separate case **claimed a reading was logged without ever calling the tool**. The champion's two "failures" were instances of appropriate caution (re-checking an ambiguous zone name, verifying a suspicious string against the real zone list), not fabrication. Full writeup: [`docs/PHASE_E_TOOL_CALLING_EVAL_RESULTS.md`](docs/PHASE_E_TOOL_CALLING_EVAL_RESULTS.md). This is a first pass (14 cases, one use-case slice, rule-based grading) — not a production certification yet.

**Production switched (2026-09-16).** `192.168.60.157:8000` now serves **`RedHatAI/Qwen3.5-4B-FP8-dynamic`** at 128K context with tool-calling enabled (`--enable-auto-tool-choice --tool-call-parser qwen3_xml`) — the first model change since this project started. Confirmed working: correct tool call on a live request, correct FP8 kernel path (not the broken DeepGEMM one), KV cache at the expected 634,799 tokens (4.84x max concurrency @ 128K). **`--kv-cache-dtype fp8` is NOT enabled** — discovered a new landmine while switching: that flag combined with tool-calling (`--enable-auto-tool-choice`) crashes with the same sm120/FlashInfer `xqa` gap documented above, even though each works fine *alone* on this exact model. Shipped with the combination Phase E actually validated (tool-calling, no KV-cache quantization) rather than chasing the extra capacity win under time pressure — see `docs/AI_Inference_Server_Build_Log_and_Roadmap.md`'s problems table for the full trace. **Action needed outside this repo**: `Operator-Portal`'s `LlmSettings.vllm_model` (or the `VLLM_MODEL` env fallback) must be updated to `RedHatAI/Qwen3.5-4B-FP8-dynamic` for the live app to actually request the right model — that's a different repo/database, not something this session touched.

### A methodology lesson worth flagging

Early long-context concurrency numbers in this repo were quietly wrong: `shapes.py` generated the *same* deterministic prompt text on every repeat/request, and vLLM's prefix caching (on by default) turned repeats into near-free cached prefills — confirmed via the server's own `Prefix cache hit rate: 81.3%` log line. Real traffic never shares prefixes like that. Fixed by making every generated prompt carry a random nonce; the corrected numbers are markedly worse (e.g. `long_long`'s peak throughput dropped from a reported ~4,000 tok/s to a real ~1,200 tok/s). The same contamination briefly produced a second, opposite-direction mistake: comparing FP8 against a BF16 baseline file that turned out to still be contaminated made FP8's TTFT look much worse than BF16's, when the corrected comparison shows FP8 is actually as-good-or-better on TTFT too. Caught before being written down as a conclusion, but a reminder that one bug can produce more than one wrong downstream number. Full story in `benchmarks/README.md`.
